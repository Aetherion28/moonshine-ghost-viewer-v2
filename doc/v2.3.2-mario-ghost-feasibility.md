# Regular Mario ghost appearance: feasibility

This is a source and asset audit, not a runtime allocation or performance test.
No renderer behavior, settings values, model vault, or heap sizes changed.

The requested third **appearance** can still mean two simultaneous runners.
Shadow Mario and Piantissimo currently each occupy a separate 90,112-byte
(`0x16000`, 88 KiB) heap. Reusing Piantissimo's heap for Mario would avoid a
third heap. Values 0 and 1 should retain their existing meanings.

The immutable model vault is already full: Shadow's 65,536-byte reservation
and Piantissimo's 73,728-byte reservation total its 139,264 bytes. Mario's
117,248-byte `/mario/bmd/ma_mdl1.bmd` is already resident in the game, and the
ghosts already borrow Mario's 199-animation table, so another asset-vault
allocation is unnecessary.

## Why a direct load does not fit

The audited Mario body contains 29 joints, 43 envelopes, 106 draw matrices,
11 shapes/materials, and 59 texture records. Its 11 materials each use five
TEV stages. Retail J3D consequently chooses `J3DTevBlock16`, even if the loader
requests a minimum of four stages.

With the same independent-data loading approach as the existing ghosts,
these known payload allocations alone are required:

| Allocation group | Bytes |
| --- | ---: |
| Double material display lists | 48,576 |
| Draw and normal matrices | 17,808 |
| Joint and envelope matrices | 3,456 |
| Material objects and blocks | 6,248 |
| 33 texture-matrix objects | 6,468 |
| Joints | 2,900 |
| Shape vertex-attribute commands | 2,112 |
| Remaining known model/shape/packet objects and arrays | 3,964 |
| **Known payload subtotal** | **91,532** |

That already exceeds the entire 90,112-byte heap. It excludes allocation
headers (at least 4,144 bytes for the counted allocations), alignment, heap
metadata, name tables, fog objects and matrix calculators. Lowering the
requested minimum TEV count therefore does not make a safe direct load fit.

The counts come from `build/mario-colour-audit/ma_mdl1.bmd`. Retail behavior
and object layouts were checked in the local decompilation's
`J3DModelLoader.cpp`, `J3DMaterialFactory.cpp`, `J3DShapeFactory.cpp`,
`J3DModel.cpp`, `J3DMaterial.cpp` and `J3DPacket.cpp` under
`build/research/sms-decomp`. The current allocation checks and heap ownership
are in `src/ghost_model.cpp` and `include/susamune/ghost_storage.h`.

## Practical next step

A dedicated prototype could use a simpler clean-Mario material pipeline or
share immutable display-list content while retaining private mutable
materials, joints, shapes and matrices. Simply borrowing the live model data
is unsafe for the current opacity and animation code: it changes material
state and root matrix-calculator pointers. The raw texture headers are also
shared by the retail loader and must not be recoloured or replaced in place.

Keep replacement under the existing render-thread quiesce and `GXDrawDone`
barrier. Prove all allocations before invoking retail constructors, whose
internal allocations are not uniformly checked for failure. Then test stage
changes, both runners, opacity, Mario's live colours and alternate body
parts. Separate hands, expressions, cap variants and FLUDD increase the scope
and are not included in this minimum body estimate.
