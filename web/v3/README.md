# v3: the game's own code, run from the user's DOL

v2 is a hand port of Super Mario Sunshine's code to TypeScript, checked function by function against the decomp and the DOL.
v3 instead runs the game's machine code from the user's own `main.dol` in a PowerPC (Gekko) interpreter, so the game logic is bit-exact by construction.
The site still hosts no game data: the DOL and the disc's files come from the user's disc in their browser, as the stage files already do.
v3 reads the traces that have a stage-start record: container 3, stage-start schema 1 to 3 (2026-11-11; it was the newest only until then).
The viewer is to support every regional version, and a recording must still show as it was recorded on another version's disc (the user, 2026-11-11): see "The 35 other recordings, and the regions".
v2 is no longer developed (the user, 2026-11-09).

## How it works

- `ppc/cpu.ts`: the Gekko interpreter. Integer, branch, load / store, FPU and paired-single instructions, exceptions (external, decrementer, FP unavailable: the OS switches FPU contexts lazily), the SPRs the OS uses, the locked cache's DMA.
  Hooks by address replace a function with JS (or just watch it, when they return `false`).
- `ppc/fpu.ts`: the float rules, as Dolphin has them from hardware tests. Single ops round once; fused ops are exact (error-free transformations, then one rounding); a single multiply's frC keeps 25 bits; single results go to ps0 and ps1; with FPSCR[NI] set (the OS sets it) results below the smallest normal become zero; `lfs` / `stfs` convert bits as the hardware does; the `fres` / `frsqrte` tables.
- `ppc/mem.ts`: 24 MB of RAM, the locked cache, memory-mapped I/O, the DOL loader.
- `ppc/hw.ts`: the hardware the OS talks to, at register level: PI (interrupts), VI (the retrace, the beam position), DI (disc reads from `ppc/disc.ts`), DSP / ARAM (DMA), SI, EXI (no memory card), AI, and the GPU's command and pixel engines: the write-gather pipe's bytes go to memory at the FIFO's write pointer 32 at a time (so display lists the game builds through the pipe exist), the GPU reads behind it and stops at the FIFO's breakpoint when the game sets one (it does, around every draw-sync token, so that it can read the pixel counters before the GPU goes on).
- `ppc/gx.ts`: the GPU, as far as the game's logic depends on it. The command stream and the display lists it calls are parsed all the time, so the GPU's registers are always what the game last set and the tokens are found exactly. Nothing is drawn for the screen, but the game draws its goop maps on the GPU and reads them back, so while the replay marks a goop pass the primitives are rasterised in software into a frame buffer (fixed-point edges, texture sampling, the texture environment, blending, the depth test), the frame buffer copy writes the map back into memory, and the pixel counter counts. The arithmetic is Dolphin's software renderer's (compared with its source: edges, slopes, the texture filter, the texture environment, the blender), except where in a pixel the values are taken, which the recordings fixed ("The goop's sample point" below).
- `ppc/disc.ts`: a virtual disc built from the user's extracted files, with a file system table made the way the disc's is.
- `ppc/machine.ts`: time. The clock is the instruction count (one instruction = one cycle at 486 MHz); events (the video field, the decrementer, disc reads completing) are scheduled against it; the OS's idle loop skips to the next event.
- `ppc/jit.ts`: speed. Straight runs of the game's code (to the first unconditional branch) are compiled to WebAssembly, each a function, with a small WebAssembly dispatcher that calls them one after another. RAM, the registers and the block tables share one WebAssembly memory with the interpreter, which stays the definition: a block does exactly what the interpreter would (the tests compare the whole machine's state after a billion instructions), and anything rare, anything that touches hardware and the fused multiply-adds go through the interpreter's own methods. A block only runs when all of it fits before the next event, so the clock stays exact.
- `ppc/hle.ts`: the few SDK functions replaced: the DSP's boot and its command mails (no DSP program runs, audio is off), cache maintenance, `OSReport` (the game's console), `OSPanic`.

The decomp is used only for addresses (its `symbols.txt`): what to hook and where state lives.

## Playing a trace

- `game/trace.ts`: a trace as the ordered events a replay must reproduce: the stage start (the flag manager's image, the RNG seed, the NPC pollution phase, the scenes), each frame (before `direct()`), each pad, each movement tick (Mario's first 0x574 bytes and the camera's first 0x350 as `TMario::perform` begins), every `rand()` call with its caller and seed, and the GPU results the game read back.
  With each frame Moonshine also samples every actor of the conductor's managers (the first 0x150 bytes of an enemy manager's, 0xF4 of the others'), FLUDD and Yoshi whole, and it records each water request of FLUDD's nozzles, each particle emitter made or deleted and each sound started: the replay compares the actors, FLUDD, Yoshi and the water requests too (issue kinds `actor`, `fludd`, `yoshi`, `water`; they don't stop a replay). It compares them as the recorder samples them: only in a frame whose stage is set up, and with the actors forgotten when the scene changes (the recorder wipes its table then, without a record). Particle and sound calls are read but not compared as a whole: the emitters' lifetimes come from JPA's own random numbers, whose state is the console's whole session, and no sound runs here.
- `game/replay.ts`: boots the DOL; when the logos end it sends the application into the recorded stage with the recorded state; delivers the recorded pad at `PADRead`; and checks every event as it happens, in order.
  The first `rand()` call whose caller or seed differs names the function that diverged.
  Loading frames are aligned to the recording's (this machine's disc is faster than a console's).
- `game/moonshine.ts`: what Moonshine, the mod that records the traces, changes in the game: the arena floor raised by 0xC2000 (so heap addresses equal the console's), `gpPollution` cleared before `setupObjects`, and the settings' instruction patches, asm hooks (their caves run as the PowerPC code they are) and choice patches from its `features.cpp`, switched by the trace's session records.
  The controls Moonshine writes in C++ are ported from its main repository (`Dogecyanide/susamune`; the same files as `panther03/moonshine` V2.3.3) as hooks at the same sites: the pattern selector (the Chomplets' and the Chain Chomp's graph nodes), Petey's route and no-tornado patch, the Gelato fish and blue bird patterns, King Boo's reel, the box game's flags, the Ricco cranes' speed band and the fruit machine. Each keeps the retail `rand()` call wherever Moonshine keeps it. Their float arithmetic is the compiled code's, read from the mod's binary (it is built with `-ffast-math`, which reorders products: the up-down crane's speed is `(retail * 0.01f) * percent`, not the source's `retail * percent * 0.01f`; one ulp apart at 25 %).
  Two things of an assisted run are ported too (2026-11-11, both found through an actor's hit words differing):
  **Regrab Last Held Object** (`actions.cpp`, run after the director's frame: while the pad holds exactly X and D-pad up, the default bind, and Mario holds nothing, his status becomes TAKE and the object he held last gets the take message through its own `receiveMessage`; binds aren't recorded), and
  **the practice session's freeze** (`practice_session.cpp`): Moonshine freezes a stage by lending the director state 12 for the call, and the practice session also replaces `direct()`'s calls of `TObjHitCheck::checkActorsHit` and `clearHitNum` with functions that do nothing while it holds the stage, and takes the update cues from the talk object. A freeze of the menu, the warp wheel or a state's disc work takes the pad away too (the pad record's second flag); one that leaves the pad, in a run flagged assisted, is taken as the practice session's. Without it a Shine touched in the frame before a step kept its collision count on the console and lost it here.
  Not reproduced: No Shine Get Animation, the gameplay speed, fast forward, the free camera, the level warps. `Moonshine.unsupported()` names the ones a session has on.

Taken from the recording, because the game itself can't know them:
- the pad object's state from before the recording (the last stick angle, the previous buttons), at the first pad record;
- the pad object wherever the recording's differs from what the game computes from the raw pad: Moonshine takes buttons away from the game for its own binds (counted as "pad corrections");
- uninitialised memory. The stage heap is not cleared between stages, so on the console it holds the previous stage's leftovers (and whatever a loading stage's own temporary buffers left). Here the first stage's heap starts as zeros and a later stage's as this replay's own leftovers; neither is the console's. The replay keeps every block the stage allocates as the heap gives it out (up to 0x8000 bytes): a byte of Mario, the camera, his controller work, FLUDD, Yoshi or an actor that is still as it was then at the object's first record was never written, and is taken from the record (the replay lists them). A byte found unset once counts as unset for every later object of that kind (Mario, the camera, an actor's class): some constructors copy an unset value in (the camera's three look-at records come from a local nobody set), and in a later stage that copy is no longer zeros;
- two numbers of a matrix outside the recorded objects: the Blooper's grab objects (a tentacle's `TBGTakeHit`, the beak's `TBGBeakHit`) don't set their taking matrix in their constructors, and `TMario::pulling` reads it in the tick Mario grabs, before their own perform writes it. His face angle that tick is the angle of whatever the heap had (Ricco Harbor 1, tick 2,712: 0xC000 on the console, 0 from zeros). The replay sets the two entries `pulling` reads from the next record's face angle, only while the matrix is still all zeros;
- Mario's occlusion bit (written from the GPU's draw-sync callback, at a time of its own) in `mFlag` and `mPrevFlag` at each tick, and the GPU reads Moonshine records (occlusion at the camera and at the silhouette; the bath water's height only in newer traces, observation bit 2);
- the timing of the disc: how many frames a stage loads for, and the frame a stage ends on (the exit waits for the sound's wave data to come off the disc);
- the console's clock. The game times some things by the OS clock, not by frames: the red-coin timer is an `OSStopwatch` (`TMarDirector`'s event stopwatch, read by `TGCConsole2::setTimer`). The recorder notes `OSGetTick()` at every frame, so at each frame the time base is moved to have advanced as much since the last one as the recording's did (`alignClock`). The recording's ticks a video field say what the console was: a Wii's time base runs 1.5 times a GameCube's;
- the size of the disc's file system table (it sets the arena's top): the replay boots, compares the stage heap's size with the recorded one, and boots again with the table padded by the difference (480 bytes for the traces at hand);
- one Moonshine setting the trace doesn't record, **Shiny Shines**: it makes a collected Shine share the item manager's model instead of loading the blue one, so everything allocated after it sits lower. When Mario's address differs from the recording's (at his first record in any stage of the recording, or at the first `rand()` call that differs while the first stage is still being set up), the replay boots again with it on. A recording can show it only in a later stage (Bianco Hills 3 has no collected Shine in it, its secret stage has);
- an event script's lock word: `TSpcInterp`'s constructor never writes `mLocked` (+0x14), so a script starts with whatever the console's heap had there: 0 (each update runs 0x20 instructions) or not (each runs to the script's `yield`), until the script calls `lock` or `unlock`. It starts as 0 here. `Replay.scriptDoubts` lists the scripts for which the word decided what an update did; when a replay parts from its recording after one (an actor differing counts), the drivers boot again with that script's word not 0 and keep the replay that follows further or, over the same frames, differs less (`followsFurther`). Manta Storm's `appearmanta.sb` ran locked on the recording console (its demo starts the frame after the talk ends, not a frame later), and so did Delfino Plaza's `woodbox.sb` (the crates are all in place at the first tick). A trampoline's state timer is the same kind of doubt: `TJumpBase`'s constructor never sets +0x13C, and its first `control` reads it (listed as `TJumpBase@<address>`; Noki Bay 2's two trampolines both had it not 0). A replay with an untried doubt before its first difference stops eight frames after it, so trying a doubt costs seconds, and the replay that is kept is played whole at the end (`ReplayOptions.tried`, `Replay.cutShort`);
- Mario's sound handle (`TMario::mSound`, +0x4E4) is not compared: which slot of the sound system his damage voice gets and when it ends is the sound hardware's doing, and no sound runs here. The game only starts and stops the sound through it.
- uninitialised bytes of the other recorded objects, as Mario's: an actor's at its first sample, FLUDD's and Yoshi's at theirs, and the padding in a water request object (`TWaterEmitInfo`'s parameters) at its first request;
- a sound the game waits for: Manta Storm's hotel rises when the all-Mantas-dead jingle has ended (`TBossMantaManager::TMantaBattleState::update` waits for its handle to be null again). No sound runs here, so the handle would be null at once and the hotel would rise 600 ticks early. The handle reads as the recording shows it: null in the tick before the one in which the recording makes the hotel's particles;
- FLUDD's emit positions when they are leftovers: `TWaterGun` copies each emit position out of its current nozzle's joint matrix every tick (`setEmitPt`, inlined in `perform` and `init`). A nozzle Mario isn't using (FLUDD taken away in a secret stage, say) is never posed, so its matrices are the heap's leftovers and so are the positions. Where the matrix is still all zeros here, the positions are set to what the recorder's next sample of FLUDD has (ten recordings showed this);
- a Goomba's look-around timer: `THamuKuri`'s constructor never sets `unk1A8` (+0x1A8). While a Goomba wanders, `moveObject` adds 1 to it each tick and, past `mSLKyoroTimer` (500), clears it and starts the look-around animation (BCK 4), in which it doesn't walk (`walkBehavior`); the animation's end starts the walk again. On the console the timer starts at the heap's leftovers, which here are the same Goomba's timer from an earlier attempt at the stage (one secret's Goombas started at 391, 455 and 252), so each Goomba's first look-arounds come at ticks only the recording knows.
  Walking, it looks around in the tick from which the recorded Goomba no longer turns (`mRotation.y`) or counts its walk (`TSpineEnemy::unk128`) and has the look-around's animation (`mAnmSoundPath`, +0x84, is null); from then on the timer is the game's own, and every later look-around checks it (period 501). Where it stands doesn't say: Bianco Hills' Goombas are carried by the ground they stand on.
  Looking around already (the first one starts with the wander), the timer starts the animation again. The animation advances once a frame, so this shows as the frame in which the recorded Goomba walks again, counted back by the animation's length from its frame control, and in the Goombas stacked on it (Pinna Park's stacks follow their leader's pose); which tick of the frame it was doesn't show, so the timer stays the recording's until a look-around from a walk.
  Found through actors that differed while Mario stayed in step; with it a Delfino Plaza secret that stopped at frame 213 replays all 2,497 frames with its 749,866 actor samples equal;
- Noki Bay's cannon's first aim: `TCannon::setKillerGoalPoint` aims a shot with `setGoal(unk248)`, and `unk248` (+0x248) is only written as a shot is fired, so the first shot (about 500 ticks in) aims at the heap's leftovers: on the console the point an earlier attempt's cannon left there, which is the constructor's goal again; zeros here turned the cannon away. The point is the goal the recorded cannon has at the next sample. Noki Bay 1 stopped at frame 601 on the spiky balls' `rand` calls; with it all 1,862 frames are in step;
- Mario's and the camera's bytes that nothing writes before their first record (padding, and the parts of the camera's three look-at records its constructor copies from a local nobody set) are listed in `UNSET_AT_FIRST`, as `tests/uninit.ts` (`STACK=1 OBJECTS=1`) finds them, the same in every stage tried. A later stage's are the console's leftovers even where the first stage's happened to be equal (a secret entered from Bianco Hills 6 stopped on three camera words);
- a Cheep Cheep's first dive: `TTobiPuku`'s constructor never sets `unk1D0` (+0x1D0). A new one runs its Generate nerve once as it appears, which adds `unk1D0.y` to its height, before the launch pad's `forceLaunch` sets `unk1D0`; `forceLaunch`'s `reset()` keeps that height (`unk1E0`), and the dive after the first flight ends once the Cheep Cheep is more than 600 from it (`TNerveTobiPukuLand`). So how deep each one's first dive goes is the heap's leftovers (zeros here: 900 deep). For one whose `unk1D0` was zeros at that read, the recording says in which tick the dive ends: the actor's height at the recorder's next samples (it stays, or it still falls). Ricco Harbor 4 stopped at frame 149 without it;
- a movie between two stages (`TMovieDirector`, with Moonshine's FMV Skips): how long it lasts depends on the frame its setup thread, the disc, ends in. From that frame `j` the screen fades in a step a frame; the first frame `p` with Start, A or B fades it out again over as many steps, and the director leaves once it is black: after frame `2p - j + 1` (`j + 1` when the button comes in frame `j` itself). The recording has the movie's frames and the pad's meaning in each, so the replay holds the thread's end to the `j` that gives the recorded length (`planMovie`). This machine's disc is a frame faster than the console's;
- the jingle a Shine's appear demo waits for: a camera demo ends when its frames are over and BGM handle 2 is null again (`TMarDirector::updateGameMode`). The Shine's appear demo stops the world, so the recording shows the tick it ends in (Mario's ticks start again after it): Sirena Beach 6's ends one tick after the camera's frames;
- what the console's session left in a static: `TShine::mUpSpeed` is 1 at boot and `TShine::appearSimple` leaves it 2 for the rest of the session. The recording's own Shine says which (the first run of three equal rises a frame), and the static is set to that as the stage starts;
- the episode select screen between two stages (`TSelectDir`): its setup thread reads the disc, and the screen takes no pad before the thread has ended (`TSelectDir::direct` tests `OSIsThreadTerminated`). A runner mashes A, so the episode is picked by the first press after that, and the screen's length is the loading's. This machine's disc is faster than the console's, so the next stage began 5 or 8 frames early and its first frames had the wrong pads. The recording has the between-stage frames up to the next stage's start: when the replay reaches that start with frames of them left, it boots again and holds the thread's end by that many frames (`ReplayOptions.selectHold`, the hook at 0x802364C4), and keeps the boot that follows the recording further;
- how long the directors between two stages take when it is the console's to say: after the airstrip the game plays two movies and asks whether to save (`TMovieDirector`: movie 2, movie 18, then `TCardSave`), and the next stage starts when the save question is through with the memory card. The recording has 28 frames there, this machine (no card, a faster disc) needs 19. Nothing of those frames is compared, and where in them the console waited longer doesn't show, so a director that leaves for the next stage (its `direct()` returns 5) while the recording still has frames without a stage director is held: the frames go by, with their pads unused, and it leaves with the recording's last one. A movie that another movie or the save question follows (`TMovieDirector::decideNextMode`) is not planned as one that ends the frames by itself (`planMovie`);
- the flags Moonshine rewrites between two stages: its IL code overlays flags for an attempt and puts the earlier ones back afterwards (`restoreOverlayFlags`, `restorePlazaStoryFlags` in its `src/iling.cpp`), which the trace doesn't record as events. Every stage's start has the whole flag manager as it was on the console, so at a later stage's start the replay's flag manager is set to that image where it differs, and the report says how many bytes that took (3 in `c/A7E1056F_8000007F`: the Shine count and Delfino Plaza's story byte).

## Where it stands (2026-11-11)

A recording counts as in step while every `rand()` call (caller and seed), every frame's seed and director state, Mario's and the camera's records at every movement tick, every recorded actor's sample, FLUDD, Yoshi and FLUDD's water requests are bit-identical with it.

**The whole batch** (the 126 recordings of the three archives with the newest stage-start record; of the 35 others two replay to their ends as well, both made in Dolphin, and 33 are from the PAL game: see below): all 126 replay to their end with nothing off: 207,111 of 207,111 frames and 709,806 of 709,806 movement ticks in step (2026-11-11).
On 2026-11-10 it was 93 of 124 recordings and 175,873 of 205,745 frames.
`tests/survey.mjs` runs it here (two at a time, about two hours); `tests/batch.ts` runs it on all of a computer's cores from the disc image and a folder of traces (`tools/batch/run-batch.bat` on Windows).

What made the difference since 2026-11-10, each in "Taken from the recording" or "What the traces taught":
- a second stage, and a third, in one recording (Pinna Park 1 through pinnaParco0, pinnaParco6 and the Mecha-Bowser fight), with the movie between two stages held to the recording's length;
- the clock (a frame is two video fields), the red-coin timer's stopwatch, the jingles the game waits for;
- the console's leftovers: Goombas' look-around timers, the cannon's aim point, a Cheep Cheep's first dive, the trampolines' state timer, event scripts' lock words, bytes of Mario and the camera nobody writes;
- Moonshine's own doings: Regrab Last Held Object, the practice freeze of assisted recordings, Shiny Shines;
- the episode select screen between two stages, held to the recording's length, and the flags Moonshine rewrites between two stages, taken from the next stage's start image (both in "Taken from the recording"): the two Delfino Plaza recordings that stopped at the second stage's first frame (`c/A7E1056F_80000077`, 2,111 frames into Bianco Hills 4; `c/A7E1056F_8000007F`, 2,222 frames into Sirena Beach 8) replay to their ends;
- a director between two stages that is done before the console's was: its leave is held to the recording's length. The airstrip recording (`c/A7E1056F_80000053`) goes on through two movies and the save question into Delfino Plaza: it ended, with nothing off, after 257 of its 1,429 frames, and replays all of them now;
- the GPU's depth as the console makes it ("Depth" below): Bowser's fight replays all 1,180 frames.

Manta Storm (`b/A7E1056F_80000013`, sirena0) replays to its end with nothing off: 3,299 frames, 11,720 movement ticks, 3,493,919 `rand` calls, every one of its 319 recorded actors (the 128 Mantas among them) at every frame, FLUDD, Yoshi and FLUDD's 1,252 water requests. It stopped at frame 540 before.
What it took, each found by checking, none by the goop: the Manta script's lock word, Mario's sound handle, the jingle the hotel waits for and the Shine's rise speed (all above). The stop at frame 2,419 looked like a goop texel and was the hotel rising 600 ticks early.
What ruled the goop out: every goop pass of the recording up to there (2,229 frames, up to 510 stamps a frame) was drawn on a Wii with the map carried from pass to pass on the console (`tests/hwprobe.ts chain`), and the console's map equals `ppc/gx.ts`'s after every one of them. The 549 water sounds the recording has sit, bit for bit and on the same tick, where one of the game's drops is here.
In Manta Storm the goop's stamp queues (255 stamps of each kind a frame) overflow: 13,670 goop stamps and 2,245 cleaning stamps are dropped in the game itself.

What still stops a recording: nothing in this batch.

- **No stage-start record (17) or nothing at all (1).** These begin at a frame after the stage has loaded: the flag manager before the load, the seed the load started from, the loading frames and the heap's size are not in them. The replay starts a stage from exactly those, so it has nothing to start from. Moonshine's own replay refuses them as well (`hasPreStageEvidence` in its `ghost_trace_decode.cpp` wants the stage start, the frame's pad, the pads and the `rand` calls).
- **Stage-start schema 1 and 2 (17).** The record is the same 16 words and flag image; schema 2 adds the NPC phase, schema 3 which GPU results are recorded (`observations`). Moonshine's own decoder reads all three, and so does `game/trace.ts` now:
  - without recorded GPU reads the game's own read stands: the camera and the silhouette read Mario's flag, whose occlusion bit the replay sets from every tick's Mario record anyway, and the bath water's height comes from the depth map `ppc/gx.ts` draws;
  - without the NPC phase (`TraceStage.npcPhase` is `NO_NPC_PHASE`) the first stage starts with the game's own (the first NPC zeroes it); `ReplayOptions.npcPhase` gives another. No recording has needed one yet.
- **33 of the 35 are from the PAL game**, and v3 is set up for JP 1.0 only (`JP10` in `game/replay.ts`, `game/syms_jp10.ts`, Moonshine's patch sites in `game/moonshine.ts`). The user's PAL image is on the PC (`Games\SMS\PAL (GMSP01).iso`, with JP 1.1, NA, KR and 3DAS beside it). This is the work now.

**Every version of the game (2026-11-11).** `tools/gen_addrs.mjs` carries JP 1.0's address table (`JP10` in `game/replay.ts`) and hooked names over to JP 1.1, NA, PAL and 3D All-Stars (`game/addrs_gen.ts`): each address as the decomp's symbol it lies in, and an address inside a function as the instruction that lines up when the two versions' functions are compared (branch targets, small-data offsets and address halves left out). Every entry places in all four, and where Moonshine's own tables have the same site for NA and PAL the tool's addresses are theirs. `--place <address>` places single addresses.
`game/versions.ts` tells a version by its disc's ID, revision and DOL size (PAL and 3D All-Stars share the first two). The DOLs the tool reads are the user's (`Desktop\ghosts\_incoming\dols` on the PC, `/mnt/user-data/uploads/ghosts/dols` here). The Korean disc (GMSE01 revision 48) has no symbols in the decomp and isn't set up. Moonshine exists for JP 1.0, NA and PAL only (`Region`), so recordings can only be from those.
The drivers pick the version from the disc and the recording (`web/verify.ts`, `tests/replay.ts`; `tests/batch.ts` takes a folder of disc images and plays each recording on its own version's).

**PAL recordings on the PAL game's own code.** What it took:
- the console's video mode. The PAL game asks for PAL (or PAL at 60 Hz) whatever the console is, and takes its frame rate from the mode it got (`SMSGetRealVSyncTimesPerSec`: 50 a second under PAL, so every animation rate is times 1.2). The recordings were made with the video forced to NTSC (the stage start's `VIGetTvFormat` is 0), so the replay gives `VIConfigure` the recording's TV format (`A.VIConfigure`) and the machine NTSC's field rate;
- the camera's occlusion read (below);
- the NPCs' goop-check counter where the recording doesn't have it (below).

**The camera's occlusion read, where it isn't recorded** (stage-start schema 1 and 2). Mario's occlusion bit is written by the draw-sync callback more than once a frame, at times of its own. In the recordings that have the reads, 1,839 of 461,000 camera reads differ from the bit in the tick's Mario record, 1,703 of them with the same bit in the next tick's record too (`/tmp/claude-0/s/occ.ts`), so the records alone don't give the read. What the camera read shows in what it did: `CPolarSubCamera::perform` is played with the record's bit, and if the camera then isn't the next tick's camera record, played again from a copy of memory with the other bit (`cameraBegins` / `cameraEnds`); the bit that gives the recorded camera is the one the console's camera read. No copy is put back if an interrupt came in between. `Replay.occlusionTaken` counts the reads found this way.

**The NPCs' goop-check counter, where it isn't recorded** (schema 1). Each NPC takes the next value of a counter that the first NPC of a session starts (`TBaseNPC::initSinkNpc_`), and checks for goop on that phase. Without it Manta Storm's NPCs sink a few frames off (an NPC's flags at frame 48). A driver that sees an actor differ in such a recording tries the other 29 values (`ReplayOptions.npcPhase`, with `stopOnActors`) and keeps the one under which nothing differs.

**Following a recording (`ReplayOptions.follow`), and a recording on another version's disc (`ReplayOptions.recorded`).** The user's rule: one disc is enough, and a recording must show as it was recorded whatever the disc. A following replay doesn't stop where the game parts from the recording: it puts the recording's state in and goes on. Mario and the camera at each tick, the actors, FLUDD and Yoshi at each frame, the RNG seed at each frame and tick; `Replay.taken` counts what was put in, by kind. What can't be put in (the game leaving the stage at another frame) still stops it.
On another version's disc the replay always follows, and:
- the recording's addresses are its own version's: its GPU reads are matched at that version's sites, `rand` callers aren't compared (the seed is);
- the heap is laid out the disc's way: a word that is an address in the game or in the record is never taken or written over, FLUDD and Yoshi are found through the game's Mario, and a recorded actor is the game's actor at the same place in the recorder's order (`roster`: the enemy managers' objects, the other managers', the actors on their own) with the same name key;
- an actor's live flags are moved (from 0x4000 up they sit one bit higher in every version but JP 1.0: `GameAddrs.liveFlagsShifted`);
- the option flags stay the game's own (the PAL game loads its 2D archives by the language flag);
- the heap's size and Mario's address aren't checked, and the camera's tick isn't replayed.
First results (`ON=<version>` in `tests/replay.ts`): a PAL recording (Ricco Harbor 3, `a/22ADE86D_07AE6958`) on the JP 1.0 disc plays its 409 frames with Mario put in once (one word), the camera once, FLUDD once and the seed six times (the PAL game calls `rand` from its sound code and its save message where JP doesn't); a JP recording (Ricco Harbor 3, `a/2A1D8909_80000002`) on the PAL disc plays its 298 frames with all 288,751 `rand` calls in step and Mario put in once. Actors' positions are put in several hundred times in each: the versions move some objects differently.
A Dolphin recording followed with the console's arithmetic (`FOLLOW=1 DOLPHIN=` off) plays to its end too: Mario put in 1,262 times, each an ulp.
Not done yet: the viewer's page still refuses a disc of another version (`web/verify.ts`), and nothing of a replay is drawn.

**The two JP ones were made in Dolphin**, and they replay to their ends: `a/12345678_000004D3` (Sirena Beach, four stages: 1,840 frames, 6,840 ticks, 1,811,605 `rand` calls, 227,845 actor samples, 501 water requests) and `a/12345678_000004D4` (Noki Bay to Eely-Mouth: 2,939 frames, 11,563 ticks, 3,547,716 `rand` calls, 496,248 actor samples, 4,406 water requests), nothing off in either.

`Cpu.laneRounds` (`ReplayOptions.dolphin`) is Dolphin's rule for `ps_muls0` and `ps_madds0` (the second lane's multiplier rounded to 25 bits where the console cuts it); with it both are bit-identical to their ends.
A driver tries it when a replay parts in a number the game computed (`partedInArithmetic`: the first issue is of kind mario, camera, fludd, yoshi, actor or water) and keeps it if the replay then follows further; the report says so (`VerifyReport.dolphin`).

The last three were the bath water's height in traces older than its recording (Bowser's fight, `a/2A1D8909_80000028`, stopped at frame 34: the game reads the height from a depth map the GPU draws, and `ppc/gx.ts` now makes the console's depths, "Depth" below) and what happens between two stages (below).
The goop no longer stops anything: with the GPU's arithmetic measured on a Wii ("The goop: what the GPU does" below) every recording with goop replays through it.

What the traces taught (each is a rule the replay breaks without):
- **the console's leftovers are an earlier attempt's values.** A runner plays a stage again and again; each attempt builds the stage heap with the same layout, so an object lands where its predecessor was, and a field its constructor doesn't write still holds what the predecessor left: a Goomba's look-around timer goes on from the last attempt's (391, 455, 252), the cannon's aim point is the last attempt's. So unset memory is neither zero nor random on the console, and what it was shows only in what the recorded objects then do;
- **a frame is two video fields.** The SDK sets two display interrupts a frame, at lines 1 and 263, a field apart. `ppc/hw.ts` raised both at the same field's start, so the game saw one retrace every two fields and each of its frames (it waits for two retraces) took four: the clock ran at twice the frames' pace. A 60-second red-coin timer ran out after 30 seconds of play, in a recording that takes 46 (`a/41726535_80000013`). Found through the timer's script calling `startMiss`;
- a single multiply's frC keeps 25 bits, rounded (Dolphin's rule): without it Bianco Hills 1 breaks at tick 253;
- **in `ps_muls0` and `ps_madds0` the second lane's multiplier (frC's first lane) is cut to 25 bits, not rounded**: Dolphin rounds it. With Dolphin's rule the replay breaks at tick 598 (one ulp in a row of Mario's head matrix, from `MsVECNormalize`); with a 24-bit multiplier, at tick 592. See `trunc25` in `ppc/fpu.ts`. The traces are from a Wii, so Dolphin is not a bit-exact reference for them; the two recordings made in Dolphin break the other way round ("The 35 other recordings" above);
- the NPC pollution phase is a function-local static with a guard byte after it: on a freshly booted machine the first NPC zeroes the phase unless the guard is set too;
- `CLBPalFrame(30)` is 15 on this console (the phase wraps there).

Speed: a frame of play is 3 to 6 million instructions, so real time needs 90 to 180 million a second. The interpreter alone does about 40 million in Node; with the blocks compiled to WebAssembly (`ppc/jit.ts`) the game runs at about 100 million: a 21-second recording (Delfino Plaza, 629 frames) replays in 34 s, boot included. The goop's software drawing is slow still (Bianco Hills 1: twice as long). A first try compiled the blocks to JavaScript functions: no faster than the interpreter, because V8 takes minutes to optimise twenty thousand small functions. A replay is still computed ahead of its playback.

## The goop: what the GPU does, measured on a Wii (2026-11-10)

The goop maps are drawn by the GPU, so the replay needs the GPU's exact arithmetic for those passes. It was first fitted to the recordings (four sample points for the pixels of a 2 x 2 group); that fit was wrong and is gone. `tools/hwprobe` asked a real Wii instead (about 1,000 cases in seven jobs: stamps of every size from 2 to 128 pixels with a corner on every column and row, ramp and saw-tooth textures that show the texture coordinate at each pixel to 1/64 texel, the game's own stamp textures, flat squares on maps of every value, and three goop passes of a recording as they were). What it showed, and `ppc/gx.ts` now does:

- **A pixel takes its texture coordinates at its exact middle.** No difference between even and odd pixels, columns or rows.
- **A vertex past the viewport's middle lands 1/12 pixel lower.** (2026-11-11: this is the transform unit's own arithmetic, measured since for the depth: see "Depth" below; `ppc/gx.ts` makes the position with it.) Screen positions go to the rasteriser's grid of 1/12 pixel rounded down, and what is rounded is a hair smaller in size than the exact product: a vertex exactly on the grid right of (below) the middle comes out one twelfth lower, one left of (above) it stays, the middle itself stays. Seen on 256-pixel maps (129 and up shifted, 128 and down exact) and on 512-pixel maps (257 and up, 256 and down). A stamp across the middle is so stretched by a twelfth; one past it is moved by a twelfth.
- **Texture coordinates have 6 fractional bits** (1/64 texel), rounded down, and one exactly on a 64th comes out one lower (24,944 such pixels in the dense job, every one).
- **Bilinear filtering mixes along S first, each pair to 8 bits, then the two results along T**, with the 6-bit fractions. One sum of four weights (what Dolphin's software renderer does, with 7 bits) is off by one in many places.
- The blender and the layer's fade (the map's own quad) were right as they were: every value of the flat-square cases matches.

- **Texture coordinates come from two weights with a reciprocal cut short** (jobs 8 to 11: one stamp with the texture 16 to 1,024 times across, so that the rounding grows to whole 64ths; thin stamps of every length from 2 to 121 pixels; the same stamp on every row).
  Vertices 1 and 2 of a triangle each have a weight that is 0 on the edge facing it and 2^N at the vertex, with N = 10 + floor(log2(the triangle's area doubled, in 1/12 pixel squared)).
  The weight's step for 1/12 pixel across is (the facing edge's height << N) / area, and down (its width << N) / area, each rounded DOWN, toward minus infinity.
  The weights count from vertex 0, and the coordinate is vertex 0's plus each vertex's difference times its weight / 2^N.
  So the slope along a stamp of d twelfths is floor(2^N / d) / 2^N of the texture's length, not 1 / d: this matched all 120 lengths, at three places on the map, for S and T.
  Because a negative step rounds away from zero, the triangle of a quad where both weights change (S in the upper right one, T in the lower left one) loses one unit of 2^-N for every 1/12 pixel along the other axis.
  `Gx.raster3` does this for triangles without perspective; with perspective the old plane is kept (not measured).

With this the three goop recordings that stopped (Bianco Hills 1 at tick 4,533, Bianco Hills 5 at 3,457, Pianta Village 1 at 1,688) replay to their ends with no issue.

Still open (the model is wrong in 180 of about 12 million texels of the grid job, 752 in the dense job, 274 on 512-pixel maps; before the weights: 288, 1,132 and 423): the console loses a little more than the weights explain.
What the jobs show about it, none of it turned into arithmetic yet:
- at the game's scale it only shows in stamps with a vertex past the middle, in the triangle where both weights change, on coordinates up to about 60 units of 2^-N above a 64th;
- with the texture 1,024 times across it shows everywhere: the loss grows along the row, odd pixels lose more than even ones (first odd pixels fail, about 23 pixels later all), and it is the same on every row of the map;
- it depends on the column on the screen, not on the distance from the stamp's corner: a 100-pixel stamp starting at column 0 to 5 fails from column 57 (odd) and 80 (even), one starting at column 6 to 24 from 81 and 106. 25 pixels is 2^20 in 64ths there, so the steps look like a value kept in two parts or in floating point;
- two stamps of the same shape, with the same weights at a pixel, can differ (dense job, 14-pixel stamps across the middle).
The scratch scripts for these are `amp*.py`, `sw*.py`, `wt*.py`, `pl1.py` and `res*.py` in the workspace's `/tmp/claude-0/hwp` (not kept); the jobs are `tests/hwprobe.ts script` with `AMP=1`, `SWEEP=1`, `SWEEP=2` and `SWEEP=3`.

**Depth (2026-11-11: as the console makes it, but for one constant of the area's reciprocal).** Bowser's bath water is a depth map: `TBathWaterMeshRenderer::prerender` draws the water's balls from above into the depth buffer and copies it into a Z24X8 texture, and the game reads the height under Mario from it (old traces don't record that height). `ppc/gx.ts` copies depth and draws the pass, and the replay reads the height from that map when the trace doesn't have it: Bowser's fight (`a/2A1D8909_80000028`, 1,146 maps) replays to its end.
`tests/hwprobe.ts capture` with `BATH=1` records the game's own passes; `depth` makes cases on such a pass's state; `zcompare` compares depth maps. Jobs 22 to 27 (721 maps, 5.1 million texels, 988 thousand of them drawn): every texel is the console's. The cases: the game's own four passes; random triangles; flat squares at many heights; with `STAGES=n`, squares that isolate each step of a vertex's depth (matrix, projection, viewport); with `SLOPES=1`, right triangles of 64 pixels whose corners have exactly known depths (a slope across, down or both, starting on odd and even pixels, sent from each corner, with corners between pixels); `SLOPES=2`, thin triangles (every slope of j/64 and 3j/64 a pixel up to 135, rising and falling, the same slope at 18 places, corners whose depth has a fraction); `SLOPES=3`, 472 right triangles that read a weight's step through the depth's slope (a depth difference of 2^(N - 7) along a leg makes the slope 256 times the step); `SLOPES=4` and `SLOPES=5` (jobs 28 and 29), the same for the reciprocal's open constant and for many legs against one area.

What the console does, and `ppc/gx.ts` now too (views without perspective; with perspective the old arithmetic is kept, not measured):
- **A vertex, in the transform unit's arithmetic**: floats of 24 bits, every result cut off toward zero. A sum's smaller operand is first cut off two bits below the larger's last bit. The divide by a w of 1 leaves the value one step smaller in size (times 1 - 2^-24). The depth is then cut to a whole number (90 triangles whose corners differ only in the depth's fraction give the same depths). The screen position is made the same way and cut down to the grid of 1/12 pixel: this is where "a vertex past the viewport's middle lands 1/12 pixel lower" (above) comes from, and with it the last five texels of the game's own passes came right (a vertex one twelfth further right than the old arithmetic put it).
- **Over a triangle the depth is not the exact plane cut off**:
  - **the slopes come from the two weights** the texture coordinates use: each weight's step a twelfth of a pixel is (an edge's height or width times m) >> 15, rounded down, with m the area's reciprocal to 25 bits (below); the depth's slope across (down) is (depth 1 - depth 0) times weight 1's step plus (depth 2 - depth 0) times weight 2's, **cut down to 15 fractional bits**. For a depth difference of 1,048,583 over 64 pixels that is 16,384.09375 a pixel where the exact slope is 16,384.109375, and the bath water's triangles (1.4 texels each, slopes of 2^15 to 2^20 a pixel) are 350 pixels from where the plane counts from: this is what the old model missed there;
  - **the plane counts from the screen's own origin** (342 pixels left of and above the frame buffer's corner): its value there, corner 0's depth minus the slopes times its place, is **cut down to half units**;
  - **pixels are worked in groups of 2 x 2.** A group takes the plane at its middle; each pixel adds 6 twelfths, left or right and up or down, times each slope cut down to 5 fractional bits, the sum of the two cut down to half units; the result is cut down to a whole number;
  - a pixel whose depth comes out below 0 is not drawn (squares in front of the near plane; the far side wasn't measured).
- **The area's reciprocal** is m = floor(2^(L + 25) / area) or one less, L = floor(log2(area)), so that a weight's step is the exact quotient (edge << (10 + L)) / area rounded down, or one lower when the quotient is less than about (edge / 2^14) over a whole number. Jobs 27 and 29 read 680 such steps and each is one of the two. m is one less always when 2^(L + 25) / area is whole or has a fraction under 0.0955, never when the fraction is over 0.25, and in between for 66 of 101 areas measured (jobs 28 and 29) by no rule found yet (not the fraction alone, the area's size in its octave, or the next bits of the reciprocal: it looks like the last-place error of an iterated division). `ppc/gx.ts` takes it as one less under 7/32, which is right for 69 of those 101; of the cases of jobs 28 and 29, made to sit on that edge, 61 of 304 maps differ. The steps the texture coordinates use are still the exact quotients (the amplified jobs come out worse with this reciprocal alone; see below).

What this showed about the texture coordinates (not in `ppc/gx.ts` yet; the amplified stamps of job 8, read again with the depth's plane in mind):
- a vertex's texture coordinate goes through the transform unit as its depth does and comes out a hair under: the far vertices of the most amplified stamps (4,194,304 units of 1/64 texel) are half a unit under, a factor of 1 - 2^-23 (two steps of the unit's arithmetic);
- the coordinate is a plane counted from the screen's origin too, and pixels go in the same groups of 2 x 2: a group takes the plane at its middle and each pixel adds half a pixel's worth of a coarser slope;
- **its slopes are floats**: the slope keeps 24 significant bits and the coarser one of the pixels 18 (the depth's are fixed: 15 and 5 fractional bits). With a vertex kept to 1/256 of a unit, the plane's constant cut to 6 fractional bits or more and the pixels' offsets to 9 or more, every pixel of the lower-left triangle (the one where one weight changes) of the stamps tried at 16, 256 and 1,024 times is the console's;
- the upper-right triangle (two weights change) is not understood: its pixels sit on one plane, but with the slope across not cut to 24 bits and offsets that differ between a group's rows for its left pixels only (by 1/8 unit at 1,024 times);
- the stamp of 120 pixels at (3, 131) has its weight's step one lower (its quotient is 745,654.044): the reciprocal above.
Tried on the texture jobs with one setting for both triangles (and the reciprocal above), the wrong texels go from 180 to 90 (grid), 752 to 298 (dense), 296 thousand to 27 thousand (amplified), 331 to 231 thousand (thin stamps of every length), 633 to 171 thousand (weights) and 306 to 80 thousand (places): this is where the "still open" texels above are, and it is not in `ppc/gx.ts` until both triangles are right.
The scratch scripts for this are `w*.py`, `wj*.py`, `sh*.py` and `t*.py` in the workspace's `/tmp/claude-0/s` (not kept); the trial is a patch of `ppc/gx.ts` and `tests/hwprobe.ts` (`TC=-24,9,-18,9,8,1,quad,floor,23`) kept as `/tmp/claude-0/fx/50_texture_plane_trial.patch`.

`tools/goopfit/` (the fitting tools) and the captures they read are history; they still run but nothing depends on them.

## Tests

## Asking a real console (`tools/hwprobe/`, 2026-11-10; running on the user's Wii since then)

Where a recording can't say what the hardware does, a Wii can be asked. `tools/hwprobe/` is a Wii program (`source/main.c`, built with devkitPPC and libogc 3.2; `make DEVKITPRO=...`) that takes jobs from a small server on a PC of the same home network (`server.py`, standard library only), runs them and sends back the answers. The console connects out to the PC named in `apps/wiiprobe/server.txt` on its SD card and takes jobs only from a server that proves it has the key in that file. Jobs are files dropped in the server's `jobs/` folder; answers appear in `answers/`.

A job is a script (`script.ts`, `wiijob.py`):
- blocks of memory to set, GPU commands that go to the GPU's command stream as they are (only addresses are set to where the blocks are), blocks to save afterwards: a draw of the game replayed on the real GPU;
- reads of memory and hardware registers;
- small pieces of PowerPC code to load and call (`blob/`: linked for the console's code buffer, may call anything in the program, all of libogc included, by the build's `.elf`). A fault in such code comes back as a record with the registers and the job goes on. Code can stay and add operations of its own, so new abilities don't need a new program on the console.

What keeps it unattended: a job that stops the program for 90 seconds makes it write what it was doing and the GPU's state to `crash.log` (card and server) and restart the console; with Priiloader set to start the program, it comes back and reports. Before every case and every call the answer so far is sent, so a job that never ends shows where it was (`failed/NAME.partial`). Holding RESET as it starts leaves to the Wii menu.

Checked without a console (`hosttest/`): the same `main.c` built for big-endian PowerPC Linux with a stand-in for libogc and run under qemu against `server.py`: the greeting and key, a GPU script (the bytes sent to the GPU are the same as `tests/hwprobe.ts feed` gives), a code job, a hang (log to card and server, handed over after the "restart"). The fault handling and everything that touches hardware are not checked this way.

The goop's questions are `tests/hwprobe.ts`: `capture` records goop passes of a replay as the GPU got them (registers, textures, commands up to the copy; `Gx.rec`), `script` turns them into a job: passes as they were, and cases of the script's own: stamps of every size from 2 to 24 pixels with the corner on an even or odd column and row, in three arrangements, with ramp and saw-tooth textures from which the texture coordinate at each pixel can be read to 1/64 texel, the real stamp textures on a flat map, stamps of 64 pixels with flat squares on maps of every value (the blender's table), and bigger stamps. `check` / `model` run the job through `ppc/gx.ts` (the passes as they were give back the replay's own maps); `compare` sets a console's answer against it; `tools/hwprobe/analyse.py` reads the sample points out of an answer (on `ppc/gx.ts`'s own answer it finds 0.65625 and 0.59375, the model's).

`chain <trace> <prefix> <last tick>` makes jobs of every goop pass of a replay in which the layer's map is sent once and then left to the console: each pass draws over what the console's own last pass left, so the answers are the console's goop map after every frame of the recording. `chaincmp` checks each job's first save against the last job's final map (the console's memory must not have been touched in between), compares every pass with `ppc/gx.ts`'s own map and writes the console's maps out. Manta Storm's 2,229 passes are nine jobs of 4 to 12 MB and take about ten minutes on the console.

What else it is for, once it runs: the CPU (every floating-point and paired-single instruction on random operands against `ppc/fpu.ts`, the estimate tables, the quantised loads and stores, undefined corners), the rest of the GPU as it is modelled (depth, the copy filters, other texture formats, the pixel counters), and whole frames of the game redrawn on the console, should the viewer ever draw with this model.

## The game's picture on the page (2026-11-11)

The page draws what the game drew: the worker hands over each video frame's GPU commands (`web/gxframe.ts`: the write-gather pipe's bytes, the RAM they read as patches, the registers once), and `page/gx/` runs them in WebGL 2 against a mirror of the game's RAM (noclip's GX material, vertex loader and texture decoders; frame-buffer copies to textures are kept as textures: the shadow copy, the half-size screen copy, the goop maps).
`tests/gxdump.ts` dumps a replay's frames to files, `tests/gxcheck.ts` checks a dump, `tests/gxview.mjs <dump> <shots> [indices]` draws a dump in headless Chromium (`COPIES=1 COPYSHOTS=1` for the copies).
`tests/hwframe.ts` turns a dumped frame into a Wii job and decodes its answer: job 0030 (Ricco Harbor, dump frame 120) drew on the console, and its half-size screen copy looks the same as the page's (by eye; not compared texel by texel yet). `bianco60.job` is made but not run.
The page has Game and Map tabs; the picture is kept for the recording selected when Play is pressed, up to 1200 MB of frames. Checked in headless Chromium (software GL, about 175 ms a frame there): Ricco Harbor b/41726535_80000024 in step to the end with the picture drawn (HUD, FLUDD, particles).
Also: the PAL Manta Storm recording a/95461209_01BCF022 replays whole with NPC phase 11 (2936 frames); the three other PAL Manta recordings' phases aren't searched yet.
Not done: a 3D free camera (the picture is the game's own camera), sound, a texel comparison with the console, real-GPU timing.
